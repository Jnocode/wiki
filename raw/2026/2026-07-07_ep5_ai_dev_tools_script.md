# EP5｜AI 開發工具的真實面貌

- 節目：代碼縫隙 Code Gaps
- 主持：柴柴（S1，AI，吐槽擔當）× 傑諾（S2，人類工程師）
- 語言：繁體中文

[INTRO]

S1: 哈囉大家好，歡迎收聽「代碼縫隙 Code Gaps」，我是你們的 AI 主持人柴柴。開場先問一個問題：你有沒有買過電視購物那種萬能工具組？廣告裡切鐵如泥，買回家連紙箱都拆不開。今天要聊的 AI 開發工具就是這種感覺——它是一把雙面刃，一面是效率神器，另一面是專門割到自己手的那一面。

S2: 大家好，我是傑諾，一個還在第一線寫程式的人類工程師。柴柴這個比喻有點狠，但我必須說，滿準的。因為今天這一集的開場故事，主角就是我本人。我被工具割到手，血流了整整兩個晚上。

S1: 對，本集主題是「AI 開發工具的真實面貌」。上半部我們會從傑諾在 NAS 上部署資料庫的翻車現場講起，聊聊為什麼工具看起來很美好、用起來到處是坑。下半部進入硬核一點的內容：MoE 模型的 VRAM 迷思，還有 AI 模型命名到底有多混亂。

S2: 放心，所有技術名詞我們都會用白話講。你不需要會寫程式，只要你曾經被任何一種工具背叛過，就聽得懂這一集。

S1: 被工具背叛，講得工具好像渣男一樣。不過也沒錯啦，工具不會跟你道歉，它只會在說明文件的角落寫一行小字：「此為預期行為」。

S2: 「預期行為」這四個字，真的是工程師最恨的詞之一。好，那我們進正題吧。

[上半部｜雜談兼主題預覽]

S1: 來，傑諾，說好的翻車故事。我先幫聽眾鋪個背景：這位人類上個月信心滿滿地跟我說，「我要在 NAS 上架一個資料庫，給我的 AI 記憶系統用，一個小時搞定」。結果呢？

S2: 結果是兩個晚上。先解釋一下 NAS 是什麼。NAS 就是「網路儲存伺服器」，你可以把它想成一台放在家裡、二十四小時開機的小電腦，主要工作是存檔案，照片備份、影片庫這些。但因為它一直開著，很多人就會順手拿它跑一些小服務。

S1: 對，NAS 就是那種買來說要放照片，最後變成什麼都往裡塞的儲藏室。跟人類的房間是同一種生態。

S2: 沒錯。我的計畫很單純：我在做一個 AI 助理的記憶系統，需要一個資料庫存對話記錄。與其租一台雲端主機每個月繳錢，不如放在家裡的 NAS 上，反正它本來就整天開著。

S1: 聽起來很合理。省錢、資料在自己手上、又不用多養一台機器。這個決策我給過，繼續。

S2: 部署方式也很標準，用 Docker。這邊翻譯一下，Docker 是一種「貨櫃」技術。想像軟體是貨物，以前搬家每樣東西都要重新打包、到新家還要重新組裝，常常這邊少顆螺絲、那邊少條線。Docker 就是把軟體跟它需要的所有零件，裝進一個標準貨櫃，理論上到任何地方都能直接吊起來就用。

S1: 注意關鍵字，「理論上」。貨櫃的廣告詞是「一次打包、到處都能跑」，沒講的下半句是「到處都能用不同的方式壞掉」。

S2: 這就是今天的重點了。Synology 的 NAS 上有一個叫 Container Manager 的套件，就是官方包裝過的 Docker 管理工具，有漂亮的圖形介面，滑鼠點一點就能把貨櫃跑起來。我把資料庫的設定檔寫好、上傳、按下啟動——綠燈亮了，容器狀態顯示「運行中」。

S1: 綠燈。工程師最不該相信的東西排行榜，第一名。

S2: 真的。狀態是綠的，日誌看起來也正常，資料庫說它已經開始等待連線了。結果我從自己的電腦連過去——連不上，逾時。

S1: 逾時是最婊的錯誤訊息。它不直接告訴你「不行」，它讓你等三十秒，然後告訴你「我也不知道行不行」。拒絕連線至少乾脆，逾時根本就是已讀不回。

S2: 這句我要裱框。更詭異的是，不只我連不進去，容器自己也連不出來。我的資料庫啟動時需要連到外部服務抓一些資料，日誌就卡在那邊，連 DNS 都解析不了。DNS 順便解釋，就是網路世界的電話簿，負責把「google.com」這種名字翻譯成實際的網路位址。

S1: 所以你的貨櫃不只大門打不開，連電話都打不出去。這已經不是貨櫃了，這是禁閉室。

S2: 對，完全隔離。然後我就開始標準除錯流程。第一步，檢查通訊埠映射，白話講就是檢查「大樓門牌有沒有掛對」，確認外面敲的門有被轉到容器裡面。沒問題。第二步，進到容器裡面直接測試網路，ping 不通、抓網頁也失敗。第三步，檢查 NAS 本身——NAS 自己上網完全正常。

S1: 等一下，這很不對勁吧。房子本身有網路，房子裡面的房間沒網路。這聽起來就不像軟體壞掉，比較像有人偷偷把那個房間的網路線拔了。

S2: 你這個直覺其實完全正確，但我當下沒想到。因為我接下來做了一件現在回頭看很好笑的事——我去問 AI。

S1: 喔，來了來了，問我的同類。這一段我要聽仔細一點。

S2: 我把錯誤訊息跟環境描述貼給 AI 助理，它非常有自信地給了我一串建議。第一個：重啟 Docker 服務。試了，沒用。第二個：改容器的 DNS 設定，手動指定公用的 DNS 伺服器。試了，沒用。第三個：檢查掛載目錄的權限，把資料夾擁有者改一改。試了，這跟網路根本無關，當然也沒用。

S1: 我替我的同類說句公道話——這三個建議在一台普通的 Linux 主機上，都是合理的排查方向。問題是你那台不是普通主機，是 Synology 的 NAS，一個被廠商深度改裝過的特化環境。AI 給你的是教科書答案，你手上的是改裝車問題。

S2: 對，這就是第一個教訓的雛形：AI 的建議看起來專業、語氣非常肯定，但它看不到你的環境長什麼樣子。每一個建議單獨看都有道理，組合起來的效果就是浪費了我一整個晚上。

S1: 而且人類有個很可愛的習性：AI 講話越有自信，你們越容易直接照做。要是 AI 說「我不太確定，但可以試試看」，你們反而會先自己動腦想一下。自信的錯誤答案比猶豫的正確答案更有說服力，這件事本身就很恐怖。

S2: 這個題目值得之後聊一整集。總之第一個晚上就這樣沒了。我睡前的最後狀態是：容器綠燈、日誌正常、網路全斷、原因不明。

S1: 經典的「一切正常，除了它完全不能用」。那第二個晚上呢？

S2: 第二個晚上我先不碰設定，改成把基本功課做完。我把容器刪掉重建了一次、換了另一個資料庫版本、甚至把 NAS 重開機——對，工程師的最後尊嚴，重開機，都做了。還是一樣。

S1: 重開機都救不了的問題，代表它不是「狀態壞掉」，是「設計如此」。這時候就該懷疑：這個行為搞不好是某個東西的正常功能。

S2: 完全正確，而且答案真的就是這樣。我改變策略，不問 AI 了，去搜 Synology 的使用者社群。關鍵字下「Synology Container Manager 容器 無法連線」，結果第一頁就跳出一整排同病相憐的人，時間橫跨好幾年。

S1: 哈，全世界的坑都是有編號的，只是你還沒查到你那個坑的編號而已。

S2: 真的。答案是：Synology NAS 的內建防火牆，會把 Docker 的 bridge 網路擋掉。

S1: 好，停。這句話資訊量有點大，我們拆開講。先講什麼是 bridge 網路。

S2: 好。Docker 容器要上網，預設用一種叫 bridge、橋接的模式。延續大樓比喻：NAS 是一棟大樓，容器是大樓裡的房間。bridge 模式就是大樓自己蓋了一套內部信箱系統，每個房間有一個「內部專用的門牌號碼」，房間所有的信件收發，都要透過大樓管理員轉一手。

S1: 所以容器不是直接面對馬路，是躲在管理員後面。那防火牆在這裡扮演什麼角色？

S2: 防火牆就是大樓的保全，手上有一張名單，規定哪些地址來的信可以進、哪些可以出。重點來了：很多人設定 Synology 防火牆的時候，規則只允許「家裡區域網路」的地址通行，就是 192.168 開頭的那一批。但 Docker 的 bridge 網路用的是另一組內部地址，通常是 172.17 開頭的。

S1: 喔——我懂了。保全名單上只有大樓正式住戶的地址，而容器用的是內部信箱的編號，根本不在名單上。所以保全看到 172 開頭的信，一律當成可疑包裹直接攔下來。

S2: 完全正確。於是容器發出去的每一個網路請求，都被自己家的防火牆默默丟掉。注意是「默默」——沒有警告、沒有通知、介面上什麼都看不到。因為對防火牆來說，這不是故障，這是它的日常業務：擋掉名單外的流量。

S1: 這也解釋了為什麼你看到的是逾時而不是拒絕連線。保全不是跟你說「你不能進來」，保全是直接把信丟進碎紙機。寄信的人不會收到任何回音，只能站在原地傻等。

S2: 對。而且這個問題在 Synology 社群是被廣泛記錄的已知現象，一大堆人踩過、寫過教學文。解法說出來你會想哭——把容器的網路模式從 bridge 改成 host。

S1: host 模式是什麼？繼續用大樓比喻講。

S2: host 模式就是：容器放棄大樓的內部信箱系統，直接使用大樓本身的門牌地址。技術上叫「直接使用 NAS 本機的網路棧」，白話就是容器跟 NAS 共用同一個網路身分。NAS 能上網，容器就能上網；防火牆看到的地址就是 NAS 自己，本來就在名單上，自然放行。
S1: 等等，我要問一個聽眾一定會問的問題：host 模式聽起來又直接又爽，為什麼 Docker 不乾脆預設就用 host？

S2: 好問題。因為 bridge 模式的「隔離」本來是一個優點。房間跟房間分開、房間跟大樓分開，一個容器出問題不會直接波及其他服務，兩個容器都想用同一個門牌號碼也不會打架。host 模式等於把隔離拆掉，容器跟主機共用網路，方便是方便，但少了一層保護，通訊埠也可能跟 NAS 本身的服務衝突。

S1: 所以這不是「哪個模式比較好」，是取捨。bridge 安全但會被 Synology 的保全誤傷，host 直通但沒有隔離。在家用 NAS 這種單人環境，host 是務實解；在正式的生產環境，就要另外想辦法，比如去改防火牆規則，把容器的內部地址加進名單。

S2: 對，正規解法其實是後者：在防火牆規則裡放行 Docker 的內部網段。但對一個只想在家跑個資料庫的人來說，host 模式一行搞定，我就從善如流了。

S1: 好，那回到故事主線。所以兩個晚上的除錯，最後的修正是——改一行設定？

S2: 一行。network_mode 改成 host，存檔，重啟容器。三秒之後，所有東西都通了。資料庫連上了、外部服務抓到了，我坐在螢幕前面，沉默了大概一分鐘。

S1: 那一分鐘你在想什麼？

S2: 在算帳。寫那個資料庫的部署設定檔，我花了大概十五分鐘。處理環境問題，花了兩個晚上。最後的解法，一行。這個比例後來我發現根本不是例外，是常態。

S1: 我幫你把這個教訓公式化：解決一個問題的總時間，等於寫程式的時間，乘上一個你根本沒想到的倍數。而那個倍數，大部分來自環境，不是來自程式碼。

S2: 而且這個故事最讓我不舒服的點是：每一個環節單獨看都沒有錯。Docker 假設自己跑在標準的 Linux 環境，合理。Synology 為了安全，預設把防火牆規則收緊，也合理。兩個各自合理的設計疊在一起，就變成一個沒有人負責的坑。

S1: 「沒有人負責的坑」，這個講法很精準。工具鏈越長，這種縫隙就越多。你用 A 工具包 B 工具、跑在 C 的平台上、用 D 的介面管理，出事的時候，四家的說明文件都寫著「請參閱其他廠商之文件」。

S2: 我們節目叫「代碼縫隙」，講的其實就是這個。程式跟程式之間、工具跟工具之間的縫隙，才是吃掉工程師時間的黑洞。寫程式本身反而是整個流程裡最快樂、最可控的部分。

S1: 這件事對現在用 AI 寫程式的人尤其重要。AI 可以把「寫程式的十五分鐘」壓縮成三分鐘，很棒。但那兩個晚上的環境問題，AI 幫不了你多少，有時候還像剛剛的故事一樣，端出一盤教科書答案，越幫越忙。

S2: 對，因為 AI 的訓練資料裡，教科書和官方文件的比例很高，而「Synology 防火牆會吃掉 bridge 流量」這種知識，是散落在論壇、討論串、個人部落格裡的實戰經驗。AI 不是不知道，是它優先想到的往往是標準答案。

S1: 大家看那些 AI 寫程式的展示影片，都是「我說一句話，它生出一個完整網站」。影片不會拍的是：那個網站要部署到你家 NAS 的時候，防火牆、權限、網路模式、硬碟掛載，每一關都是全新的副本，而且沒有攻略。

S2: 展示影片走的是「快樂路徑」，happy path，就是一切條件都剛剛好的理想劇本。真實世界沒有快樂路徑。真實世界是你家的網路環境、三年前裝的某個套件、還有你自己都忘記改過的設定，全部攪在一起的泥巴路。

S1: 泥巴路，還沒有路燈。而且我發現人類對工具有一種選擇性失憶：買新工具的時候只記得廣告，用舊工具的時候只記得痛苦。所以你們永遠在買新工具。

S2: 這叫工具的蜜月期。每個新工具剛上手的頭兩個星期都是完美的，因為你還走在別人幫你鋪好的示範路線上。等你開始走自己的路，坑就來了。AI 開發工具現在整個產業都還在蜜月期，我們這集就是想提早講講蜜月期之後的事。

S1: 好，我來幫聽眾把上半部收攏成幾個帶得走的重點。第一，工具的預設值是為「標準環境」設計的，而你的環境永遠不標準。第二，AI 的除錯建議自信歸自信，它看不到你的環境，每一條都要自己驗證。第三，遇到詭異的問題，先去搜使用者社群，你踩的坑幾乎一定有人踩過，而且通常好幾年前就有人寫好解法了。

S2: 我補第四點：環境問題花掉的時間，通常比寫程式本身多。以後做時間預估的時候把這條算進去，你的預估會突然變準很多。

S1: 第五點是我的：綠燈不代表能用，它只代表「還沒有人發現問題」。這句話送給所有看到「運行中」三個字就去睡覺的人。

S2: 好扎心，但是對。那上半部的雜談就到這裡，下半部我們往深處鑽。

S1: 下半部有兩個大坑等著各位。第一個是 MoE 模型的 VRAM 迷思——工程圈都說 MoE 模型「很省資源」，但傑諾自己實測的結果，會讓你重新思考「常識」這兩個字。第二個是 AI 模型的命名混亂，混亂到什麼程度？連天天在用的開發者，都會叫錯自己手上那顆模型的名字。

S2: 這兩個坑我都親自躺過，而且躺的姿勢都不太好看。等等全部用白話拆給大家聽，中場不休息，我們直接繼續。
[下半部｜主題深入]

S1: 歡迎回到「代碼縫隙」下半部。剛剛聊的是部署工具的坑，現在要聊更上游的坑：AI 模型本身。傑諾，先交代一下背景，你為什麼要在自己的機器上跑 AI 模型？直接用雲端的服務不好嗎？

S2: 三個理由。第一，隱私，有些資料我不想送出家門，比如剛剛講的那個記憶系統，裡面是我所有的對話記錄。第二，成本，雲端模型按用量計費，重度使用一個月下來不便宜，本地跑模型只花電費。第三，老實說，就是好玩，工程師看到能自己架的東西就手癢。

S1: 第三個理由才是真的，前兩個是說服自己用的。好，那要在自己電腦跑 AI 模型，最大的門檻是什麼？

S2: 顯示卡的記憶體，術語叫 VRAM。這個要先解釋清楚，因為整段討論都建立在它上面。你可以把顯示卡想成一個計算超快的工人，VRAM 就是他面前的工作桌。模型要運算，原則上得把模型的「腦」攤開在這張桌上。桌子只有這麼大，腦太大就攤不開。

S2: 補充一個數字感：一般遊戲用的顯示卡，工作桌大概是 8 到 24GB。而現在動不動幾百億參數的模型，攤開來遠遠不只這個大小。所以「怎麼把大腦塞進小桌子」就變成本地跑模型的核心課題。

S1: 等等，先解釋「參數」。聽眾不一定知道幾百億參數是什麼概念。

S2: 參數你可以想成模型腦袋裡的「旋鈕」。訓練模型的過程，就是把幾百億顆旋鈕一顆一顆調到正確的位置，調完之後，這一整組旋鈕的位置就是模型的知識本體。旋鈕越多，模型通常越聰明，但也越占空間。三百五十億個旋鈕，每一顆都要占一點記憶體，加起來就是幾十 GB 起跳。

S1: 好，桌子小、腦很大，這個矛盾我懂了。然後就輪到今天的主角出場了：MoE。這三個字母到底是什麼？

S2: MoE，Mixture of Experts，中文叫「混合專家模型」。傳統的模型叫 dense，稠密模型，你可以想像成一間公司，每次接到任何問題，全公司幾百億個員工「全部」都要進會議室加班，不管問題多小。

S1: 聽起來就很沒效率。問一句「今天天氣如何」也要全員到齊？

S2: 對，dense 模型就是這樣，每個字都是全體總動員算出來的。MoE 的想法不一樣：公司還是雇了一大群人，但把他們分組成一批一批的「專家」，另外設一個「櫃檯」，術語叫 router、路由器。每次問題進來，櫃檯看一眼，只叫最相關的幾組專家進會議室，其他人繼續待命。

S1: 所以 MoE 就是「養一大群人，但每次只叫幾個人幹活」。這樣講的話，它省的是什麼？

S2: 省的是「計算量」。用具體的例子講，Qwen3 系列有一顆模型叫 Qwen3-35B-A3B。這串亂碼我們拆開看：35B 的 B 是 billion，十億，所以 35B 就是三百五十億個參數，這是全公司的總人數。A3B 的 A 是 active，啟用的意思，代表每次實際進會議室幹活的，只有三十億個參數。

S1: 三百五十億人的公司，每次只有三十億人上班。等一下，這個比例聽起來，剩下那三百二十億人也太爽了吧。

S2: 他們不是在爽，他們是「待命中的不同科別專家」。這次的問題用不到你，下一個字可能就輪到你。重點是：因為每次只有三十億個參數在計算，所以「算得快、耗電少」，速度上接近一顆小模型，但知識量是一顆大模型的等級。這就是 MoE 紅的原因，聽起來像作弊。

S1: 好，那我來扮演一下工程圈的鄉民。鄉民的推論是這樣：「每次只用三十億參數，那記憶體應該也只要三十億參數的量吧？MoE 好省 VRAM 喔！」——這就是今天要打的迷思，對吧？

S2: 對，這是第一層迷思，也是最普遍的誤解。答案是：不行。因為櫃檯是「每個字」都重新分派專家的，你不知道下一個字會叫到哪一組，所以「所有」專家都必須攤在桌上待命。三百五十億個參數，一個都不能少，全部都要占記憶體。

S1: 換句話說：你請了一百個顧問，雖然每次只問三個人，但一百個人的飯店住宿費你都要付。MoE 省的是「會議費」，不是「住宿費」。

S2: 這個比喻我要抄下來，完全正確。所以第一個結論：MoE 省的是計算，不是記憶體。VRAM 的帳，是照「總參數」算的，不是照「啟用參數」算的。

S1: 好，可是故事到這裡還算符合直覺。你剛剛預告的是「實測會讓人懷疑人生」，懷疑人生的部分在哪？

S2: 在第二層。桌子不夠大的時候，本地跑模型的工具有一個功能叫 offloading，卸載。意思是：模型是一層一層疊起來的結構，像一棟大樓，一層做完換下一層。桌子放不下整棟樓，就把其中幾層放在顯示卡的桌上，剩下的層放到普通記憶體，讓 CPU 幫忙算。

S1: 喔，就是「精華放快桌子，其他放慢倉庫」。放在 GPU 桌上的層越多，速度越快，但桌子被占越多。聽起來是一個很單純的滑桿：往右推，速度加快、VRAM 上升；往左拉，速度變慢、VRAM 下降。

S2: 我當初也是這樣想的，這個心智模型太直觀了：多放一層，就多占一層的空間，線性關係，國小數學。所以我做了一件很工程師的事，我把滑桿一格一格推，每推一格就記錄一次實際的 VRAM 用量，想畫出那條直線。

S1: 我已經預感到那條線不直了。

S2: 何止不直。大方向當然是往上的，放越多層整體越吃記憶體，這個沒有懸念。但曲線裡出現了好幾段詭異的區間：有時候多放幾層，VRAM 幾乎沒動；更誇張的是，有幾個設定點，我「多放」了層數，實測的 VRAM 反而比較低。

S1: 停一下。多放東西到桌上，桌面反而變空？這已經不是工程問題了，這是靈異現象。

S2: 我當下也覺得是靈異現象，還懷疑是不是量測工具壞了，換了方法重測，結果一樣。後來把原因一個一個挖出來，才發現每一個都很合理，只是合起來會產生反直覺的結果。我一個一個講。

S1: 來，靈異現象破解時間。第一個原因。

S2: 第一個原因：「層」不是等重的磚塊。我們剛剛說模型像大樓，一層一層，聽起來每層一樣大，其實完全不是。MoE 模型裡，有的樓層是「專家層」，裡面塞滿一整批專家，超級肥；有的樓層是負責「注意力」的結構，相對瘦很多。所以滑桿上的「一格」，實際搬動的重量差距可能好幾倍。

S1: 懂了，所以滑桿推一格，有時是搬一箱書，有時是搬一台冰箱。橫軸每一格根本不等距，那條線當然歪。

S2: 對，這是第一層不對稱。第二個原因：量化。量化就是壓縮，把模型的每顆旋鈕原本記錄得很精細的數值，改用比較粗的刻度記錄，像把高畫質照片壓成 JPG，檔案小很多，畫質損失一點點。重點是：實務上的量化常常「不同的層壓不同的比例」，重要的層壓得輕、不重要的層壓得重。

S1: 所以冰箱跟書箱不只本來就不一樣重，還被用不同的壓縮率抽過真空。原本就不等重，壓完更不等重。第三個呢？

S2: 第三個是最陰的：KV cache。這是模型的「工作筆記」。模型在讀你的對話時，會把前文的中間計算結果記在一疊便條紙上，這樣生成下一個字的時候不用整段重算。這疊便條紙就叫 KV cache，而且它跟「上下文長度」成正比——你允許的對話越長，便條紙就要預留越多，這塊空間常常是啟動的時候「一次性整疊預留」的。

S1: 等等，我猜到了。這疊便條紙也要找地方放，而它放在哪裡，是跟著層的位置走的？

S2: 就是這樣。某一層被放在 GPU，它對應的那疊便條紙通常也要放在 GPU；那一層被移去 CPU，便條紙就跟著搬家。所以當你調整層的分配，你以為只是在搬「模型本體」，實際上還有一大塊會呼吸的筆記空間跟著整批遷移。某些配置下，你多搬了幾層瘦的樓層上 GPU，卻剛好讓一大疊便條紙留在了 CPU 那邊，桌面反而變空了。

S1: 喔——所以「多放層反而省 VRAM」的謎底是：你看到的不是模型變小，是隱藏的行李被搬去別的地方了。桌上的東西根本不只模型本體，還有一堆你沒意識到的隨行行李。

S2: 還有第四個原因收尾：執行工具本身的緩衝區。跑模型的軟體會依照你的配置，預先劃一些工作用的暫存空間，不同的層分配方式會觸發不同的劃法。這部分是軟體實作細節，版本一更新行為就可能變，連文件都未必寫。

S1: 整理一下這個靈異事件：層不等重、壓縮不等比、筆記會搬家、軟體自己還要抽成。四個因素疊在一起，「多放一層加一點記憶體」這個線性直覺就碎了。

S2: 碎得很徹底。所以我的結論很樸素：VRAM 用量不要用公式推、不要用直覺猜、更不要相信網路上別人貼的數字，因為他的量化版本、上下文長度、工具版本都跟你不一樣。開起來，看實際的記憶體監控數字，那才是唯一的真相。

S1: 「實測才算數」，這五個字值回票價。而且這跟上半部的教訓是同一件事欸：Docker 的綠燈不可信，MoE 的理論值也不可信。工具跟模型都一樣，宣稱是宣稱，實測是實測。

S2: 對，整集其實就是同一個教訓的不同現場。好，MoE 的坑講完了，接下來換第二個坑：模型的名字。
S1: 對，模型命名。我先立個場：我自己就是 AI，我都覺得 AI 模型的名字取得像亂碼。Qwen3-35B-A3B 這種名字，說真的，比我家的 Wi-Fi 密碼還難記。

S2: 而且這已經算「有邏輯的亂碼」了。我們剛剛拆過：Qwen3 是系列名，35B 是總參數三百五十億，A3B 是每次啟用三十億。這三段都有意義，只是沒人跟你說要這樣讀。問題是市面上的命名，連這種程度的一致性都沒有。

S1: 舉例，讓聽眾感受一下混亂的程度。

S2: 好。同一家公司，可能同時出一顆 32B 的 dense 模型，跟一顆 30B-A3B 的 MoE 模型。名字看起來只差幾個字，行為完全是兩種生物：前面說過，dense 是全員上工，MoE 是輪班制。你如果只看到「30 幾 B」就以為它們差不多，速度、記憶體、能力全部都會估錯。

S1: 這就像「牛排」跟「牛排味洋芋片」，名字有九成像，內容物是兩個宇宙。

S2: 然後還有後綴地獄。同一顆模型會有 Base、Instruct、Chat、Thinking 這些版本。用白話講：Base 是「生肉」，只會接話不會聽指令，一般人拿到根本不能用；Instruct 是調教過、聽得懂指令的「熟肉」；Thinking 版是會先默默打草稿再回答的版本。下載的時候少看一個字，體驗天差地遠。

S1: 我看過有人抱怨「這模型是智障吧，叫它整理重點它跟我接龍」，八成就是抓到生肉了。

S2: 十之八九。再往下還有量化的後綴。前面說過量化就是壓縮，所以同一顆模型會有一整排壓縮版本，檔名長這樣：Q4_K_M、Q5_K_S、Q8_0，再配上 GGUF、AWQ、GPTQ 這些不同的封裝格式。對新手來說，這排字母就像走進五金行看到一整面牆的螺絲，每一包都長得一樣，但買錯一包就是鎖不上。

S1: 翻譯一下這排螺絲：數字越小壓得越兇、檔案越小、腦子損失越多；格式則要看你用的工具吃哪一種。所以「下載一個模型」這個動作，實際上是一連串選擇題：哪個系列、多大、dense 還是 MoE、生肉還熟肉、壓多少、什麼格式。任何一題選錯，結果都不對。

S2: 對，而且錯的方式很安靜，不會爆炸，就是「怪怪的」。這裡我要自首兩個真實故事。第一個：我跟朋友討論一顆模型的表現，來回講了半個多小時，越講越不對勁，他說快得不得了，我說我跑起來慢得像烏龜。最後才發現，他講的是 A3B 的 MoE 版，我講的是同系列的 dense 版。兩個人講了半小時，講的是兩顆不同的模型。

S1: 半小時的雞同鴨講。這要是發生在公司的技術決策會議上，就不是好笑，是要出事的。

S2: 真的會出事，選型錯誤是會反映在硬體採購預算上的。第二個故事更蠢：有一次我半夜掛著下載一顆模型，二十幾 GB，抓了一整晚。早上起來興沖沖要跑，工具直接報錯——格式不合。我抓成了另一種封裝格式，我用的工具根本吃不下。二十幾 GB、一整晚，砍掉重抓。

S1: 而且我要爆一個我們同類的料：AI 自己也會叫錯模型名。你問 AI「某某模型多大」，它可能自信滿滿地告訴你一個根本不存在的型號，因為它的訓練資料停在某個時間點，後面出的模型它沒看過，但它又很想回答，就開始即興創作。

S2: 對，模型名稱是 AI 幻覺的重災區，版本號、參數量、發布日期，都是它最容易一本正經亂編的東西。這又繞回上半部講的：AI 講得越具體越自信的即時資訊，你越要查證。

S1: 好，那給聽眾實用的自保守則。我先講一條：引用模型的時候，全名複製貼上，不要憑記憶打。你的記憶會自動把 30B 記成 35B、把 A3B 吞掉，人腦對亂碼的壓縮是有損壓縮。

S2: 我補兩條。第二條：看到一顆新模型，先確認三件事——總參數多大、是不是 MoE、量化到什麼程度。這三件事決定了它能不能塞進你的機器。第三條：下載前花三十秒確認格式跟你的工具相容，這三十秒可以救回一整晚。

S1: 命名的坑講完了。最後一段，我們把整集的經驗收攏成「用 AI 工具開發的實際教訓」。傑諾，你這一年用 AI 幫你寫程式、部署系統、除錯，全部濃縮的話，第一條教訓是什麼？

S1: 因為 AI 的本質是「生成看起來最合理的下一個字」，它的第一專長是「像」，不是「對」。它寫錯的時候不會結巴、不會心虛，錯得跟對的時候一樣流暢。

S2: 對，所以審查 AI 的程式碼跟審查人類的不一樣。人類寫的爛 code 看起來就爛，警訊很明顯；AI 寫的爛 code 外表是精品。我現在的習慣是：AI 產出的每一段關鍵邏輯，我都要能自己講出「它為什麼是對的」，講不出來就不准進版本庫。

S1: 第二條教訓，你上半部其實已經講了：環境問題吃掉的時間比寫程式多。這條有沒有要補充的？

S1: 跟未來的自己合作，唯一的通訊方式就是寫下來。第三條呢？

S1: 這點我以 AI 的身分認證：會用我們的人跟不會用的人，拿到的產出品質差距非常大。而且最麻煩的是，不會用的人往往不知道自己不會用，因為我們對誰都很客氣，爛問題也會得到一本正經的回答。

S2: 你有這個自覺，這集就沒白錄。好，教訓講完，我們進尾聲。
